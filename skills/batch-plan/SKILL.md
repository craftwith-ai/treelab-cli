# batch-plan — turn the need into a roadmap

Prerequisite: the start context shows a feature worktree and its current batch. Otherwise, explain the problem and only suggest `lab new <project> <lane>`; plan nothing in the main checkout.

## First batch of the lane

1. Read the context, the lane brief if one is named (`docs/lots/<lane>/brief-<date>.md`, filed by `lab new --brief`), the neighbouring flat batch files that are named (`FLAT_BATCHES=`), `docs/masterplan.md`, `docs/treeplans/<lane>.md`, the current batch and the code strictly needed, so as not to ask questions whose answer already exists.
2. Apply `grill-me` before any code, to the decisions still open: detailed questions without jargon (what the choice changes, each option in plain words, every technical term explained in its context), asked with `AskUserQuestion` in Claude, as numbered text in Codex; a first round of ten questions at most; one single extra round of five questions at most if an important decision is still open. The answers are the agreement: summarise your understanding and go on without waiting for a confirmation. Guided lane (`guide=first` in `.lab/meta`, opened by `lab new --guided`): the first-lane skill replaces this round — five questions at most, no grill-me, one single batch.
3. With `use-goal`, check the overall goal and its evidence in the masterplan; complete them only during the initial framing of the project. An additional lane reads them without rewriting them.
4. Split the whole request into ordered batches, each one small enough to fit in a session without compaction. Write the order, the intent and the exit criterion of each batch in `docs/treeplans/<lane>.md`, with its links to `docs/lots/<lane>/`. No progress symbol: state lives in the batch file only and `lab plan` computes the view. Respect the batches already seeded and write in no other lane.

## Each batch

0. Start of batch, before any write: apply `grill-me` only to the decisions of this batch still open (none: no question) — detailed questions without jargon, asked with the multiple-choice question tool (`AskUserQuestion` in Claude, never as text: under a Goal, a question in text ends the turn and the Goal starts it again), as numbered text elsewhere (Codex, which then creates its Goal with `create_goal`, use-goal skill). A gesture asked of the user outside the session (a sign-in, a key) goes through the same tool. The answers are the agreement: show the summary of the decisions and go on without waiting. It is the only moment of the batch where the user is expected; everything else runs without them. A guided lane (`guide=first` in `.lab/meta`) asks no grill-me here, no second round: the first-lane skill already asked its questions, and what remains open takes the simplest option, written as a decision.
   Execution line, never a question, no line: the Mac, the default. Under the State line, write `**Execution** : cloud` only by choice, for a batch that runs without the user nor the Mac (code and tests alone), or `**Execution** : mac — <need>: <detail>` to name why the batch needs the Mac, the need taken from the closed list `secret` (an API key, `.env`, a production secret), `deploy` (`lab deploy`), `mac-tool` (chip acceleration, Mac app, keychain, Chrome extension), `human` (a human gesture during the batch), `resource` (a local resource declared in `resources=`, `lab lock`), `live` (an urgent or very interactive batch the user follows live, deduced from this grill-me). `lab next` reads it, keeps the Mac on `lab deploy` or `lab lock` in the Steps even under `cloud`, and announces its choice; `cloud=no` (`lab cloud <project> no`) remains the switch that keeps every batch on the Mac.
   Before writing a cloud line, read the needs remembered for the project — `cloud-needs=` in the startup context, `NEED=` lines of `lab cloud <project>`: each one is a need a Cloud session ran into (`blocked: need <need>: <detail>`). A batch that will meet the same need stays on the Mac, `**Execution** : mac — <need>: <detail>` naming it; `lab cloud <project> needs reset` forgets them, never on your own initiative.
   Blind spots: before freezing the plan, name what could make it wrong (edge case, real data, another lane, environment) and file each one as a criterion, a risk or out of scope.
1. Read the Handoff of the last closed batch, `docs/lots/<lane>/CHANGELOG.md`, then measure the code concerned.
2. Apply `use-goal` to set a single result for the batch and its observable success criteria. Do not confuse activity ("modify the form") and result ("a person can send the form without error").
3. Fill in the batch file: goal, scope, out of scope, measurable criteria numbered `C1`, `C2`…, steps with test, tests to write, screens to check and risks. A batch that adds a test command also declares it in `.github/workflows/ci.yml` (`FAST_CMD`, `TARGETED_CMD`, `FULL_CMD`, `E2E_CMD`). If evidence files are expected (screenshots, measurements, outputs), plan the report `docs/lots/<lane>/preuves/lot-NN-<slug>.md` right now.
4. Read the line `Interface : <folders> · screens : <widths>` of the project's `AGENTS.md`; missing or still in a comment, fill it in first if the project has an interface. If the batch will change one of those folders, `better` is available for planning; write in "Screens / paths to check" the screens concerned and the sizes from that line, never a fixed pair. Otherwise, write "No screen".
5. Check `LAST_BATCH` in `lab status <project> <lane>` after completing the treeplan (intent written: a new lane no longer shows `unknown`). If this batch is the last one planned, announce that a check together will follow; prepare the lane's acceptance paths. A permanent lane (`PERMANENT=yes`) always shows `LAST_BATCH=no`: no acceptance follows, each batch is delivered by its own PR. If the batch needs a shared resource (simulator, local database, port) or produces generated files, check their declaration (`resources=`, `generated=`, `regen=` in the project config) and plan `lab lock`.
6. Leave the batch file planned, in the language of its State field (`planifié` under `**État**`, `planned` under `**State**`); no index to mark. The same session then codes and closes the batch (Final report).

## Final report

Explain the confirmed goal, the complete roadmap, the batch ready and what is left. Show all batches. Then apply batch-run in this same session, without waiting for an answer.

Exception, only when the batch file says cloud: instead of batch-run, run yourself, from your session — even if it does not run in the lane's tab — `lab next <project> <lane>`: it records the batch files and opens the run on a Cloud machine (from the lane's session, it replaces it). The heavy-context rule of batch-run also goes through `lab next`, for a fresh session. A refusal names the cause and the document: fix it, then run it again. No prompt to copy nor command to have typed; only if `lab next` refuses for a reason you cannot fix, or outside cmux, give it to be typed.
