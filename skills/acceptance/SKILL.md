# acceptance — try together before closing

Acceptance covers the result of the whole lane. The last batch is technically closed; the folder and the tab stay open. Read its treeplan, the batch files and the `## Lane acceptance` section of the last batch. `lab status <project>` recomputes the phase; an older approval does not count for a new result.

## Have it tried

- Summarise simply what works, what the user can try and what remains uncertain. Launch the real result in the lane's visible tab; suggest a first concrete path.
- Before the trial, record the useful code and documents: the worktree must be clean, because the tried revision is `HEAD` at the moment the decision is written down. With external documents (`docs=local`), `lab next` recorded the lane's batch files when it opened the acceptance (`DOCS_COMMIT`); the **Docs revision** is taken after this `DOCS_COMMIT`, by `lab acceptance` itself. With `docs=repo` as with `docs=local`, you take no revision and run no `git commit` for the acceptance. Make no commit between the trial and the decision: it would change the tried result.
- An online trial runs on a declared assembly: `lab deploy <target>` from the lane (`--with <lane>` keeps another lane served), never a raw deployment; `SERVED=` and `lab status` say what is served, `--dry-run` what would be lost. A target not yet declared is set up with `lab deploy --add <type> <target>`, then `--dry-run`.
- Note `recette=production` from `lab next` (production is the CI that deploys the branch targeted by the PR, `staging` if it exists, otherwise the base; no `deploy.` target): follow it — in a project with a tower, the tower merges the PR; otherwise the user merges it on GitHub (never a git command to type); you wait for that branch's deployment, the trial happens in production, then `lab acceptance --accept` and `lab close`, which delivers the record through a dedicated PR.
- Each path suggested names the `Cn` criteria it tries.
- Retro: each defect found during acceptance becomes a test that would have caught it, or a line of `AGENTS.md` if it cannot be tested; the fix quotes it.
- Gather the user's feedback and explicit decision. No answer keeps the acceptance open. Do not create a Goal that would try on its own to obtain an approval or to close the lane.
- Write down the decision with `lab acceptance <project> <lane> --accept --evidence <path tried, approval received>` (repeatable), or `--reject --feedback <feedback>`: it takes the tried revision, writes the single `## Lane acceptance` section of the last batch file following the [record template](../../templates/project/recette.md), records it alone and reads back `ACCEPTANCE=valid|refusee`. Never `--accept` without the user's explicit approval. No extra state file, no acceptance in the treeplan.
- lab writes the `Validated by` line (`Validé par` in a French batch file) itself: the role it computes (`user`, `tower`, `lane agent`), then the typed evidence it checked — never a person's name, never by hand. Typed evidence: `--evidence check:` (lab runs `acceptance_check=` of the project config, on the tried revision, clean tree required after it) and `--evidence screens:<batch>` (screens filed by `lab proof <project> <batch> add`, fingerprints checked again).
- The agreement itself is kept by lab outside the lane, in its state (`$LAB_STATE/<project>/agreements/<lane>`, tied to the tried revision and batch); the `Validated by` line is only its trace. A section written or rewritten by hand records no agreement: in a project with a tower, the tower then asks the user again before closing.
- The user's own words are their agreement: when they write in this tab, or in the tower's, that the acceptance is validated or the lane can be closed (for example `recette validée, couloir à fermer`), lab's hook records their exact words outside the lane (`$LAB_STATE/<project>/words/<lane>`, tied to `HEAD`, valid one hour, `LAB_WORDS_TTL`) and a `LAB:` context names what to run: `lab acceptance <project> <lane> --accept` — no `--evidence` needed, lab writes `words: "…"` and `Validated by: user — words "…"`, the agreement `via=words close=yes` — then `lab close <project> <lane>`, without `--confirm` and without asking again. A question, a negation, a long message or a command never counts; unclear words: ask with the choice tool, buttons whose labels repeat the lane in their language (`Close <lane>`, `Keep <lane>`): lab reads the click. Commit nothing between their words and `lab acceptance`: the revision would change and the words would no longer count. Never type their words yourself (`cmux send` of them is refused).
- In a project with a tower, accepting belongs to the tower (on typed evidence) or to the user's own words read by lab: without them the lane agent's `--accept` is refused, nothing written; its `--reject --feedback` stays open. When the lane touches the interface, file the screens of the tried paths with `lab proof <project> <batch> add --step screens <files…>`: the tower shows them to the user and accepts on their yes.

## Fix a piece of feedback

Record the acceptance record before changing batch. Open the fix in the same lane: `lab next <project> <lane> --batch <fix> --kind fix`. Run from the still-live acceptance session, the same command replaces that session in its tab, once the record is recorded.

The CLI keeps the unmerged result and adds the batch to the lane's treeplan only. Do not rewrite the Handoff in advance to announce this fix: let the CLI create the batch. The new session applies batch-plan, then batch-run and batch-end. A new acceptance follows the fix.

## Record an approval and close

1. After an approval of the result actually tried, run `lab acceptance <project> <lane> --accept --evidence …`. A detail added afterwards in the acceptance section alone keeps the approval; a change of code, of another file or of another section requires a new trial, and `lab close` checks it.
2. With `LAB_DOCS`, the record stays in the external documents repository. If it is not versioned, explain what is missing and keep the lane; do not create a mirror in the project.
3. An approval of the result is not, on its own, a request to remove the folder and the tab. First run `lab close <project> <lane> --dry-run`: it lists all the obstacles at once (`OBSTACLE=`) without changing anything; fix them before asking anything. When the CI workflow gates the full suite behind the `full-suite` label, `lab close` posts it if missing and delivers only once that suite is green on the exact revision (`FULL_SUITE=`; `pending` arms the watcher). On `RESULT=ok`, present the lane's name and this consequence, then get the closing approval if it has not already been given. After this explicit approval, run `lab close <project> <lane> --confirm <lane>`. Do not ask again for an approval already received for this same action and this same result. On the user's own words (agreement `via=words`), close it yourself at once: `lab close <project> <lane>` without `--confirm` (`CLOSED_BY=words`), from this session too — the lane's tab closes with this session once the lane is delivered and removed (`ACTION=armed`: the watcher does it after the CI). A red night refuses it and names its button: ask once, buttons `Close <lane> despite the red night` and `Keep <lane>` in the user's language; on that click run `lab close <project> <lane>` again, lab writes the agreement and its reason; never `--night-red-ok` from an agent. Otherwise, in a project with a tower, the closing is the tower's: `lab close` is refused to the lane's agent, and the user's agreement recorded by `lab acceptance --accept` is the closing order. Tell the user it is over for them: the tower closes the lane at its next round (`WAITS_FOR=close`), without asking again; never ask them for a second yes, a terminal or a command. A question or a permission still waiting in the lane holds the closing until the user answers it.
4. Without a tower and without a closing approval, keep the lane. After a technical refusal, report the reason and the recovery action given by the CLI; bypass neither the acceptance nor the checks. Only the branches attributed to the lane and proven delivered are removed; older references that cannot be attributed stay intact.

The final closing ensures delivery and the targeted removal. Do not run an earlier merge to bypass its checks (single exception: the merge made by the user under the note `recette=production`); `next`, `sweep` and SessionStart close nothing.
