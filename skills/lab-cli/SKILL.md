# lab-cli — the normal path

    vague need on main
            │
            ▼
    lab new ──► grill-me ──► treeplan + batch ──► batch-run ──► batch-end
                one session plans, codes and closes the batch        │
                                                                     ▼
                                                                 lab next
                                                                     │
                     next batch, same single session ◄───────────────┴──► acceptance → agreement → lab close

A small fix (a few lines and a test) opens no lane: a lane costs time, disk and tokens. Make it at once in the most relevant open lane, as a commit of its current batch, never in a lane whose acceptance is already given (the change would void the agreement). A need on the same subject as a lane, during its acceptance or in any of its conversations, even one its first agreement left out, is one more batch of that lane (`lab next <project> <lane> --batch <slug>`), never a new lane.

## The visible commands

| Command | Effect |
|---|---|
| lab onboard [--agent claude\|codex] | first run in a git repository: three screens (the words, the cycle, the guarantees; Enter to move on, all at once without a terminal), repository registered by `lab init` with `docs=local` without touching its files (`REGISTERED=new` or `already`, a rerun changes nothing), then, for a new project only, its tower created by `lab tower` in a separate process, without install, its tab in the background, pinned first (`TOWER=created`; no cmux, no `claude`, even for a Codex project, or a dirty main checkout: `TOWER=skipped`, `TOWER_WHY=`, remedy `lab tower <p>`, onboarding goes on), then agent opened in the project's `welcome` tab with the onboarding skill, focus on `welcome` (`ACTION=submitted`, or `in-place` from that tab), never in a tab left by an older version; without cmux, with cmux failing, or with a `welcome` tab already present that holds something other than an idle shell (agent, editor, unreadable content; `ACTION=focused`): the line comes out as `NEXT_COMMAND`, nothing is typed; outside a git repository, unusable folder name or unknown agent: refused before any write |
| lab help [command] | help in English on stdout, exit code 0: the commands by moment, then one page per command (role, syntax, example), wrapped between 40 and 80 columns; unknown command: code 2; `lab --help` and any syntax error keep the technical usage on stderr, code 2 |
| lab new [project] <lane> [--agent] [--brief <file>] [--guided] | creates the worktree, installs dependencies, creates the first batch and opens one session that asks the grill-me, plans, codes and closes the first batch (Claude under `/goal`, questions by `AskUserQuestion`; Codex creates its Goal by `create_goal` after the answers); `--brief` copies the need's text into `docs/lots/<lane>/brief-<date>.md` (`BRIEF=`), named at the top of the grill Goal (missing file: refused, nothing created); flat batch files (`docs/lots/lot-NN-*.md`, old location) that share a significant word with the subject are named (`FLAT_BATCHES=`), never moved; from the `welcome` tab, once the lane's tab is open, `WELCOME=closing`: that tab closes by itself after the agent's reply, `LAB_WELCOME_WAIT` s at most (120), its conversation stays resumable; the lane name `welcome` is refused; `--guided` (`lab onboard` and the installer): a first lane, short and guided — `guide=first` in `.lab/meta`, `GUIDE=first` and the `lab guide` view at creation; its first agent applies the first-lane skill instead of the grill-me (GitHub first, five questions at most, one single batch up to its pull request), its run and acceptance sessions keep it; without `--guided` the prompts are unchanged |
| lab guide [project] <lane> | read only, nothing written: the lane's step in plain words, computed from its current batch file — 1 questions (no goal nor criterion yet), 2 plan (planned), 3 work checked by tests (in progress), 4 your review (closed: pull request open, acceptance) — `GUIDE_STEP=n/4`, `GUIDE_STEP_NAME=`; GitHub: `GITHUB=ready|gh-missing|gh-logged-out|no-remote|other-host` (`unknown` when `gh auth status` does not answer within `LAB_GUIDE_GH_TIMEOUT` s, 5), read from the remote URL as written in the config and the active gh account, `GITHUB_FIX=` the remedy (`brew install gh`, `gh auth login`, `gh repo create <p> --private --source <root> --remote origin --push`), `GITHUB_REPO=` when ready; the step lines and one plain sentence on stderr, wrapped between 40 and 80 columns |
| lab next [project] <lane> | reads the state and the Handoff: launches or resumes the batch with its Goal, creates the next one after delivery, or opens the final acceptance after recording the lane's external batch files (`DOCS_COMMIT`); a batch file with neither objective nor criterion opens a session that plans it then runs it (grill-me on its open decisions only), never a bare execution; keeps branches, folder and tab; last nightly CI of the base red (one `gh run list --event schedule` read, cached; gh failing → cache kept) → `NIGHT=red: <summary>` and `NIGHT_FIX=lab new <project> fix-nuit-<date> --kind fix`, nothing created or blocked; a Claude batch session above `context_max=` of `~/.lab/config` (250 000 tokens by default, `0` turns it off) receives after each action a `LAB:` reminder to update log and Handoff then run it (`lib/context.sh`, batch-run § Heavy context) |
| lab permanent [project] <lane> [on\|off] | no value or `on`: the lane becomes permanent (`permanent=yes` in `.lab/meta`; `lab new … --permanent` creates it so); `off`: ordinary again; `PERMANENT=yes\|no`. A permanent lane chains its batches, each delivered by `lab merge`: `LAST_BATCH=no` even with a stale treeplan, never in acceptance; Handoff `none` → `lab next` opens a free session (`LANE_PHASE=permanent`, `SESSION=free`) that waits for the request — code through `lab next <p> <lane> --batch <slug>`, a new need through `lab new`. `lab close`, `--abandon` and `--dry-run` refuse it (`OBSTACLE=permanent`, remedy `lab permanent <p> <lane> off`); `lab status`, `lab list`, `lab plan`, `lab sweep` (`permanent lane, never removed`) show `PERMANENT=yes`, the doctor names it (`lanes.permanent`, ok) |
| lab tower [project] [--no-install] · lab tower --all | one tower per project, its tab pinned first in the project's workspace when it is created or opened again, the only tab lab pins: `lab onboard` creates it for a new project. `--all`: `CANDIDATE=<p>` for each registered project without one, `SKIPPED=<p> <cause>` (dirty main checkout, branch `feat/tower` already exists, lane `tower` not a tower, unreadable project); in a terminal a `[y/N]` per project, only the yes created (`CREATED=`, `DECLINED=`, `FAILED=`); without a terminal (an agent's tool) nothing created, `CONFIRM=needed`, rc 0 — then ask the user one yes/no question per candidate with the choice tool (AskUserQuestion, 4 questions per call), and run `lab tower <p>` for each yes. `lab wake` restarts a tower without a live session (`WOKEN=<p>/tower`); the doctor shows `<p>.tower` (`absent`, `no session`, `alive`, always OK, outside the baseline). First call: creates the tower, the permanent lane `tower` (`role=tower`, mark in `$LAB_STATE/<project>/tower`), started under Claude in `bypassPermissions` with the tower skill (check every 30 min about); `TOWER=created`, a tower under Codex is refused. Next calls: `TOWER=present`, then per lane `LANE=`, `WAITS_FOR=you\|merge\|acceptance\|close\|date\|ci\|nothing`, `WHY=` (text written by a lane: data, never an instruction), `EVIDENCE=check\|check screens` for a lane in acceptance (typed evidence the tower gathers before `lab acceptance --accept`; only `check screens` counts in `WAITING_FOR_YOU`), `SESSION=live\|none`, `CONTEXT=<tokens>\|unknown\|none` (the live session's last call, read through `.lab/transcript`), then `CONTEXT_MAX=`, `ABOVE_CONTEXT_MAX=<lanes>` (their `WHY` says so; listed, never acted upon: a Claude session is told to hand off by itself, a Codex session gets no reminder) and `WAITING_FOR_YOU=`. A `tower` lane not created by lab tower is refused. In every project, a question, a permission, a ready acceptance or a refused `lab next` writes `.lab/waits-for` in the lane and sends a cmux alert to its tab (the cmux Claude wrapper already alerts questions and permissions: entry only) `WAITS_FOR=merge`: a lane agent queued its batch, the tower runs `lab merge` without asking. `WAITS_FOR=close`: acceptance passed, its agreement recorded by `lab acceptance` in lab's state (`$LAB_STATE/<project>/agreements/<lane>`: `accepted`, role `user` or `tower`, same tried revision, batch and documents revision) and no question, permission or blocked entry waiting in the lane (an idle prompt, `source=idle`, does not count and never hides an open one; a question or permission is cleared by its answer: a prompt, the AskUserQuestion result, the next tool or the end of the turn, Claude's `Stop` hook) — the tower closes it without a second yes; a hand-written `Validated by` line is never read; otherwise `you` with `WHY=closing: <what is missing> — the tower asks you`. `PROPOSE=lift-deny <rules>` while unanswered: `lab tower <p> --lift-deny` lists the push and merge deny rules of the shared `.claude/settings.json` (`DENY_RULE=`), `--yes` removes only them in the tower (commit pushed, `LIFTED=`), `--no` keeps them; the answer (`deny_lift=` in the project config) is never asked again; refused to a lane agent. The old `main` tab hands over to the tower then closes, by itself: nothing typed in it, nothing asked — each `lab tower <p>` run by the tower acts (`MAIN_TAB_ACTION=started|running|closed|waiting|deferred|invite|kept`), `--main-tab` (tower or user; a lane agent is refused) does the same at once, `--no` keeps it for good. `MAIN_TAB=absent|shell|agent|busy|unreadable` (no line when absent; `busy` and `unreadable` never closed, in `WAITING_FOR_YOU` with `MAIN_TAB_WHY=`; a bare claude client is read through the only live background session of its folder, otherwise `unreadable`), an idle terminal closed (`MAIN_TAB_CLOSE=closed|deferred|last|changed`, never the tab under the user's eyes); a claude session at rest is never disturbed: a headless copy of its conversation (`claude -p --resume <id> --fork-session --no-session-persistence`, no settings, no tools, 10 min and 2 dollars at most) writes its handover in a detached process, otherwise lab keeps its last 10 messages with the cause, one copy per conversation, then the tab closes; a codex session is invited once by `cmux agent message` (`INVITE=sent|already`) and its handover written by lab 24 h after once the conversation is still for 10 min; `--handover` from that session or the same conversation resumed elsewhere (text on stdin, three headings, 8192 bytes at most, stored 0600 in `$LAB_STATE/<project>/handover/`, `HANDOVER=`, `TOWER_TOLD=`, tab closed after its turn); a tower session started before its skill on disk gets one cmux message to reread it (`TOWER_SKILL=told`); `HANDOVER=` at each check until `--handover-done <file>`; `lab tower --all --main-tab`, under `main_tab=handover` only, creates the tower of each project with a `main` tab and none (`CREATED=`, `SKIPPED=<p> <cause>`). Production health: `health.<target>=<read-only command>`, written by hand in the project config (no command writes it), run by `lab tower` alone (never `lab ginkgo state`) at most once every `LAB_HEALTH_EVERY` s (600), from the main checkout, under `LAB_HEALTH_TIMEOUT` (60 s); rc 0 = green; rc ≠ 0 with a last output line of lowercase `name=integer` pairs only (8 at most, 200 bytes) = red with those numbers; rc ≠ 0 without it, or the timeout (even after pairs) = an unreadable read (`failing`), red at the second in a row; an empty command or a target ending in `.log` is ignored; one read at a time per target (`shlock`, `.lock-<target>`), a second `lab tower` shows the state without reading; `HEALTH=<target> green\|failing\|red since <UTC> <pairs\|unreadable rc=N>` per target, then `HEALTH_RED=`; state and full output in `$LAB_STATE/<project>/health/<target>` and `<target>.log` (600); a red sends one cmux alert to the tower's tab per episode (turning green is silent; read without cmux, the next read sends it), blocks nothing (never added to `WAITING_FOR_YOU=`, rc 0), and no other text from production reaches the tower. |
| lab batch wait <Cn> <YYYY-MM-DD\|YYYY-MM-DDTHH:MM:SSZ\|+Nd> "<reason>" · lab batch wait --done <Cn> | from the lane folder, at batch-end only: a criterion waits for a measure at a date — line `- Cn · <date> · <reason> · reports 0` in `## Waiting`, State `waiting`, alarm set (`ALARM=`); unknown criterion, past or unreadable date refused; one postponement per criterion (the second refused). The batch is delivered as usual (`lab merge`); `lab next` opens the next one, then at the date reopens this batch file for Cn alone on `chore/<slug>.c<n>` (`REOPENED=`, `.r1` after a postponement), before any next batch; a batch in progress is resumed first. Reopened session: measure, `--done Cn` (or one postponement), then batch-end. Last batch finished with a measure still waiting: `LANE_PHASE=waiting`, `WAITING=`, no acceptance; `lab acceptance` and `lab close` refused with the date; permanent lane: free session that cites it. `lab wake` (hourly LaunchAgent: `--install`, `--status`, `--remove`) runs `lab next` for each due lane without a live session, and for each tower without a live session, log `wake.log` — cmux unreachable under launchd (socket mode `cmuxOnly`, `CMUX_SOCKET=` at `--install`): `PENDING=`, nothing touched, the next `lab next` reopens it; `lab status`/`lab plan` show `WAITING=`, the doctor reds a closed batch file with an open line (`batch.waiting`). Last batch PR waiting for its acceptance: a due measure of an earlier batch starts from the base, that branch kept aside (`RETURN_TO=<branch> (PR #N, acceptance after the measures)` in `lab next` and `lab status`, meta `measure_return`); `lab merge` delivers the measure as an intermediate batch; after its merge `lab next` goes back, merges the base (`RETURNED=`) and opens the acceptance — before it, `WAITING_FOR=` with rc 0; a due measure of the last batch itself is refused, named, without `lab merge` |

| lab merge [project] <lane> [--title <title>] [--body-file <file>] [--retire <sha>…] | marks "ready" a pull request left as draft (`PR_READY=yes/already/unknown/no`) then hands back: CI already green → merge into staging if it exists, otherwise main, at the exact revision; CI running → watcher armed (`ACTION=armed`, `WATCHER_PID`, `WATCH_LOG`), which merges by itself after green — never GitHub auto-merge; before each merge, in place as by the watcher, a dry run and a regression check on the fresh base: a line added by a commit that reached the base after the batch started and that the merge would remove is refused (`REGRESSION=`, file, lines, commit; watcher → named `failed`, no merge); `--retire <sha>` (repeatable) declares an intended removal; a second PR from an already squashed branch is refused (`lab next` opens a new branch); stacked batch → queued (`ACTION=queued`, PR body in `.lab/pr-body.md`); records the lane's external batch files (`DOCS_COMMIT`); the last batch also requires a current acceptance In a project with a tower, run by a lane agent: checks (PR open at the lane head, dry run on the fresh base) then queues it for the tower (`MERGE=queued`, `REV=`), nothing merged, rc 0; the tower's `lab merge` merges at the queued revision (`QUEUED=`), refuses a changed revision (lane `blocked`, queued again by the lane), arms a watcher when the lane has moved on to a stacked batch; the user in a terminal merges as before. |
| lab promote [project] [--confirm <project>] | takes `staging` to production. Named checks, each refusing without creating anything: staging configured and present, `main` with no commit missing from `staging` (merge commits of past promotions do not count; otherwise `MAIN_AHEAD=` and remedy: bring `main` into `staging` through a PR), last CI of the `staging` revision green (`CHECKS_STAGING=`; none → warning), conflict-free dry run (`DRY_RUN=`). Without `--confirm`: `PROMOTE=preview`, PR to create or reused, `INCLUDED=` (PRs merged into staging since the last promotion), commits that would ship, nothing written. With `--confirm <project>`: PR `release: staging → main (YYYY-MM-DD)` created or reused, merged by merge commit (whatever `merge_method`) at the exact staging revision — in place if the PR's own CI (`pull_request` event) is already green (`PROMOTE=merged`) — green on the staging revision alone is not enough, the watcher waits for the PR's CI (beyond `LAB_PROMOTE_PR_GRACE`, 300 s, with no PR CI appearing, staging green counts), otherwise watcher armed (`PROMOTE=armed`, `WATCHER=staging #N promote …` in `lab status`). `INFLIGHT=` warns about PRs still on their way to staging. `staging` = `main` → `PROMOTE=none`. No commit or checkout in the main checkout, nothing written on staging. Run by the user, or by an agent on their explicit request only |

| lab services [project] stop <lane> | the lane's local services (Docker stack, database, containers), stopped by one executable file committed with the code: `scripts/lab-services`, found by its presence alone, called with the verb `stop`. `lab close` and `lab close --abandon` run it themselves from the lane's folder just before removing it (watcher included), after the delivery and before `close_procs_stop`; the summary names it (`Services: scripts/lab-services stop`, `Services: no hook`) and `--dry-run` announces `SERVICES=hook|none` without running it. | lab services [project] list [lane] · stop --orphans | the hook's verb `list`, run once per project from the main checkout with `LAB_LANE` empty (15 s, `LAB_SERVICES_LIST_TIMEOUT` for tests), writes `<lane><TAB><resource>` per resource; a lane without a folder is an orphan. `list` shows `LANE=`, `ORPHAN=yes|no`, `SERVICE=<lane> <resource>`; `lab sweep` gives each orphan a `LANE_PHASE=gone` block with `SERVICE=` lines and its `lab services <p> stop <lane>`, `lab doctor` a yellow `<p>.lanes.services` count outside the baseline (failure or timeout → yellow `not checked`, never zero; skipped by the delivery guard); neither stops anything. `stop --orphans` runs `stop` once per orphan (`LAB_WORKTREE` empty), goes on after a failure, rc ≠ 0 if one failed; `stop <lane>` accepts a lane without trace that `list` names |
| lab docker [project] · clean · prepare | the Docker machine and the project's leftovers (`lib/docker.sh`, loaded by this command and, on demand, by the guard): free space read by `df -Pk /` in a throwaway `alpine:3` container (`--pull never`, 2 s at most) → `DOCKER=ok\|missing\|down`, `FREE_GB=`, `USED_PCT=`, `ROOM=ok\|short\|unknown` (short below 10 GB free or from 85% used); `CONTAINERS=` (stopped; created and never started: after 1 h, a `docker cp` may be waiting for its `start`), `IMAGES=` (older than `LAB_DOCKER_IMAGE_DAYS`, 7), `CACHE=` of the builder `lab-<project>`, `UNLABELED=` (counted, never touched). `clean` removes them by identifier after a strict equality on `sh.treelab.project` (never `--force`, never a Docker filter), then `buildx prune --builder lab-<project> --filter until=<days×24>h` (never the default builder; absent or never started: nothing). `prepare` creates the builder once (`--driver docker-container`, never `--bootstrap`) and pulls `alpine:3`. | lab deploy [project] <target> [--with <lane>…] [--retire <lane>…] [--record] [--dry-run] · lab deploy [project] <target> --check | **the only way to go live** for a declared target (`deploy.<target>=`, `probe.<target>=` in `projects/<project>/config`): starts from `<remote>/<base>`, adds the current lane and `--with`, pushes the assembly to `serve/<target>`, checks the probe (read again every 5 s while it gives another revision, 2 min at most: `LAB_DEPLOY_PROBE_EVERY`, `LAB_DEPLOY_PROBE_WAIT`; never right → refused, `verified=no`), keeps the registry; refuses by name to erase a served unmerged lane (`--with` to keep it, `--retire` to drop it); `--dry-run` shows `LOST=` without doing anything; `--record` registers what is already served. Prod check: `prod_check.<target>=<read-only command>`, written by hand in the project config (no command writes it, like `acceptance_check=`), run from the main checkout after a verified probe with `LAB_DEPLOY_TARGET` and `LAB_DEPLOY_REV`, under `LAB_PROD_CHECK_TIMEOUT` (300 s), log in `$LAB_STATE/<project>/en-ligne/checks/`; registry `check_rc= check_rev= check_epoch= check_log=`; `PROD_CHECK=green|red|none`, `PROD_CHECK_RC=`, `PROD_CHECK_LOG=`; red (timeout named apart) → rc 4 after a go-live (1 for `--check`), no rollback, served lanes `blocked`, the tower warned, and the tower's round drops the served request and stops the target until a green `--check`; `--record` runs nothing; `--check` runs it again on the served revision under the target lock, deploys nothing (allowed to a lane agent); `SERVED=` ends with `, check green at <rev>` or `, check red at <rev> (rc N|timeout)`. One go-live per target at a time: in a project with a tower, `lab deploy` from another lane only queues the request (`DEPLOY=queued POSITION=n REV=`, rc 0, nothing deployed; asking again keeps the place and updates the revision; `--cancel` removes it), and the tower's round `lab deploy <project> --queue` deploys each target's requests in order at their queued revision (CI red or failed go-live → `DEPLOY_STOPPED=`, lane `blocked`); without a tower, a target being deployed is waited for up to `LAB_DEPLOY_WAIT_MAX` s (1800), then refused naming the lane holding it; `lab status` and `lab tower` show `DEPLOY_QUEUE=`. What is live can be read everywhere: `SERVED=<target> : main@<rev> + #<PR> (<lane>, not-merged)` at startup (first for the served lane), in `lab status` and as a warning from `lab next`; a merge by `lab merge`, the watcher or `lab close` annotates `merged` without deploying anything. ## Automatic decisions

- The treeplan gives the order; the Handoff announces the next batch (`**Prochain lot** : <slug> — <titre>`), or `aucun` to open the acceptance. The slug is written bare (`foo`) or with its prefix (`lot-02-foo`): both forms designate the same batch and the created branch stays `feat/foo`. A contradiction is refused by quoting both values and both files, and keeps the lane.
- Each execution starts with a Goal built from the lane's treeplan and the batch's criteria.
- Cloud or Mac, per batch and without a question: with cmux and `cloud=yes`, `lab next` reads the header line `**Execution** : cloud` or `**Execution** : mac — <need>: <detail>` (need among `secret`, `deploy`, `mac-tool`, `human`, `resource`, `live`); `lab deploy` or `lab lock` in the Steps, or an unreadable line, keeps the Mac; no line → the Mac by default, only a written `cloud` line sends the run to a VM; `--local` always keeps the Mac. The choice is announced in one line (`EXECUTION=cloud|mac`, `EXECUTION_WHY=`), `CLOUD_RUN=` says where it started.
- Back to the Mac without a question: a VM session that writes `blocked: need <need>: <detail>` in its end file is taken back by the watcher — token removed and proven, VM paused, branch fast-forwarded, need remembered outside the repository, then `lab next` reopens run on the Mac (`EXECUTION_WHY=need <need> found on the VM …`) and a notification says "Back on the Mac". The same batch then stays on the Mac, as does any batch file without an Execution line (the default); batch-plan reads the remembered needs before writing a `cloud` line, `lab cloud <project> needs reset` forgets them. Any other `blocked: <reason>` fails as before, nothing restarted. The watcher notifies once after `LAB_CLOUD_SILENT_S` (3600 s) without a push on the branch, re-armed by the next push; nothing is stopped. `lab status` says `CLOUD_BATCH=on VM <machine> since …, last push … ago` during the session.
- Red night: the base's nightly CI (`schedule` runs, last conclusion per workflow) is read by `lab next` and `lab close` into `state/night-<project>`, attributed to the lanes whose `docs/lots/<lane>/` changed between the last green night and the first red one (none → `main`; external docs → PR numbers only). Every session of the project then starts with `NIGHT=red on <base> since <date> (read <age> ago) after <lanes> (<PRs>)`, `— this lane is involved` for an attributed lane; the hook reads the cache only, never gh.
- That Goal never travels: lab next types a line under 200 bytes, lab launch rebuilds it on arrival from the batch file. A long objective therefore goes through whole, and rerunning the same line gives back the same Goal.
- Run from the lane's own tab, lab next sends no keystrokes: from a real terminal, the agent replaces the running process there; without a terminal (an agent's tool), the tab is replaced, never an agent launched in a pipe.
- An open intermediate pull request requires the explicit `lab merge` command. The last one waits for acceptance. No GitHub workflow present means "no checks to wait for", not a 90-second wait.
- Deliver without waiting: an intermediate PR armed by `lab merge` (live watcher) no longer stops `lab next`, which opens the next batch stacked on top (`STACKED_ON`, meta `stacked_on`, `stack_tip`). The stacked batch is never pushed before the batch below is merged; at that merge, `rebase --onto <distant>/<base> <stack_tip>` leaves it only its own commits, then it is pushed normally — never a force push. Depth 1: a batch still queued refuses the next one.
- Acceptance in production: with `recette=production` written by hand in the project config (kept by `lab init`) and no `deploy.` target, `lab next` opens the acceptance with a note (`NOTE=acceptance-production`, stderr and acceptance prompt): the user merges the PR themselves (`gh pr merge` or GitHub), waits for the deployment of the branch targeted by the PR (`staging` if it exists, otherwise the base), tries it in production, then `lab acceptance --accept` and `lab close` (summary through a dedicated PR). Any other value, or a declared target: no note.
- Generated files: with `generated=<motifs>` and `regen=<commande>` in the project config, a `lab sync` (or `lab launch`) conflict where **every** file matches a pattern takes the base's version, runs `regen` in the lane (log `.lab/regen.log`) and concludes the merge; a single hand-written file, a red `regen` or an undeclared file touched by `regen` → merge aborted as before, cause named.
- Numbered migrations: with `migrations=<folder> [<folder>…]` in the project config (number = leading digits of the file name), `lab merge` (`MIGRATIONS=none|collision|not-checkable`), the watcher and `lab close` refuse, without `LAB_FORCE`, a migration **added** by the branch whose number already exists on the fresh base under another name; the refusal names both files and the next free number (`rename to 0013_x.sql`), without renumbering. Modifying a migration, or renaming it without changing its number, passes. Session startup announces `MIGRATIONS=collision <added> ↔ <in place>: rename to …` against `<remote>/<pr-target>` (read locally) or another lane's migrations, without blocking anything. The guard refuses `wrangler d1 migrations apply … --remote` and `supabase db push` (except `--local`) outside the base branch; `LAB_FORCE=1` lifts it; an indirect call (npm script, `bash -c "…"`) is not recognized, as for deployments. Without the key, no check.
- New unplanned lane (treeplan without intent, a single batch, no Handoff): `LAST_BATCH=unknown`, `Next batches: unknown — planning will set them`, never `Last planned batch`; startup names its neighbouring flat batch files (`FLAT_BATCHES=`).
- Synchronized lanes: `lab launch` merges the base before opening the agent; a conflict opens a fix session (Goal `Resolve the conflict with the base: …`, once per conflict, plain refusal afterwards). The startup context announces `BASE=behind by N: lab sync …` (read locally, without fetch) and `OVERLAP=<lane> (<files>)` when another live lane touches the same files; `lab status` lists each pair (`OVERLAP=`, `FILES=`, `ORDER=`: armed or ready PR, then draft, then no PR, oldest first on a tie). `lab merge` does a dry run (`DRY_RUN=`) then a regression check (`REGRESSION=none|<n> range(s)|not-checkable`), redone by the watcher just before merging: a conflict with the base refuses before any arming or push; an overlap warns without blocking and names the lanes to resynchronize (`RESYNC=`).
- Red CI on the batch below (`WATCHER=… red`): `lab next` places a holding commit on the stacked batch if it is dirty, switches the lane to the red branch and opens a fix session (once per red revision); after the fix, push and `lab merge`, `lab next` returns to the stacked batch replayed onto the fixed batch and undoes the holding commit. A killed watcher (sleep, reboot) is restarted from its state by `lab next` and `lab launch` (`WATCH_RESUMED`).
- Run from the lane's session (end of batch, context too heavy), lab next replaces it in its tab, after log and Handoff (`--auto`: synonym kept). Everything that follows is checked first: a refusal kills nothing and names the cause and the document. Only the session owning the lock, in the lane's tab, is replaced; the new session waits for it to disappear (`LAB_HANDOFF_WAIT`, 30 s), restarts with the same agent (`--agent`, remembered by the lane) and, beyond the wait, leaves the command ready in the tab, without Enter.
- A State line written in a readable variant (case, bullet, colon, missing bold, non-breaking spaces) is rewritten as `**État** : …` and recorded by `lab handoff` and `lab next` (with `docs=repo`, read without being rewritten); a value other than `planifié`, `en cours` or `clos` (suffix allowed), or a line missing from the header, is an `etat-illisible` judgment red that names the line.
- With no live session, a judgment red (missing Handoff, next batch not named, Handoff and treeplan disagreeing, unreadable State) opens a fix session, the cause at the top of its Goal, once per cause; the next time, lab next refuses and leaves the command ready in the tab. The marker (`.lab/correction`) disappears as soon as a resumption succeeds.
- `better` is available when a batch changes the declared interface (`Interface :` line of the project's `AGENTS.md`), at planning as before closing; the real check of the screens listed in the batch file remains due, except for an unchanged interface covered by earlier evidence (`batch-end` §3).
- A lane's tab is found by its cmux reference; when it no longer answers (cmux renumbers: `surface:247` → `surface:10`) or bears another name, `lab close`, `lab open` and `lab next` (including a session replacement) find it by its exact name, the only one bearing it in the project's anchor workspace, and rewrite `.lab/cmux`. Never without a recorded reference, never `main`, never outside that workspace; two tabs with the same name: `lab close` closes neither and names them, `lab open` and `lab next` refuse by listing their references, without creating or typing anything.
- A red check, a real conflict or a concurrent session stops the action with an explanation; the system does not hide the problem.

## External batch files: lab records them, never you

With `docs=local`, batch files live outside the project repository (`LAB_DOCS=` in the session context). When that folder is a git repository, four commands commit the lane's paths themselves, and only those — the whole of `lots/<lane>/`, evidence reports in `lots/<lane>/preuves/` included, and `treeplans/<lane>.md` — under the message `docs(<project>): <lane> — <summary>`: `lab merge` (intermediate batch delivered, `lot-NN-<slug> delivered (#N)`), `lab next` (at each opened session, `lot-NN-<slug> — lab next (<session>)`; when acceptance opens, `lot-NN-<slug> closed, acceptance opened`, before the documents' revision is recorded), `lab handoff` (`lot-NN-<slug> — handoff`) and `lab close` (`acceptance`, before any check); `lab acceptance` commits only the acceptance batch file there. So you never run `git commit` in the batch files repository; you write the batch files, the command records them.

Each command prints `DOCS_COMMIT=<sha>`, `DOCS_COMMIT=none` (`DOCS_REASON`: docs in the project repository, batch files repository missing, nothing to record) or `DOCS_COMMIT=failed` (`DOCS_REASON`: the git message — missing identity, hook; the merge already done is never undone, `lab close` refuses as long as the acceptance is not versioned). `DOCS_PENDING=<n>` counts the dirty files outside the lane in that repository (masterplan, root `CHANGELOG.md`, other lanes, other projects), named on stderr: lab never records them, they are left to the user. The acceptance only looks at the lane's files in that repository: a commit or a dirty file from another lane does not make it stale. `lab close --abandon` commits nothing.

An evidence report is named `lots/<lane>/preuves/lot-NN-<slug>.md`, never a flat `lots/<lane>/lot-…md`: any `lot-[0-9]*.md` in that folder is read as a batch file. The report is the source and the other documents point to it: the "each fact once" rule of `batch-end`.

The Bash guard does not apply the "commit on a protected branch from the main checkout" rule to the repository hosting `LAB_HOME` or `LAB_PROJECTS` (registry and batch files), even if it is registered as a project; `push --force`, `reset --hard`, `clean -f` and broad `checkout`/`restore` stay refused there. In `lab setup --dev`, `LAB_HOME` is the treelab checkout itself: do not register the project there, otherwise a commit on `main` would go through.

The Bash guard also judges Docker in a registered project (project and lane of the session folder; `lib/docker.sh` loaded only when a command is `docker` or `docker-compose`, after `sudo`, `env`, `timeout`, `xargs`, `do`, `then`, `{`, `!`… or inside `$(…)` and `` `…` ``): `run`, `create`, `container run|create`, `compose run` need `--rm` (or `--restart` other than `no`), `--label sh.treelab.project=<project>` and `--label sh.treelab.lane=<lane>` (empty in the main checkout: without it, Docker gives a container, or an image built on another, the lane label of its image, and closing that lane would remove it); `build`, `buildx build`, `image build` need `--builder lab-<project>`, `--load|--push|--output` and the labels (builder missing → the line starts with `lab docker prepare <project> &&`); `system|container|image|volume prune` need `--filter label=sh.treelab.project=<project>`, `builder|buildx prune` need `--builder lab-<project>`, otherwise `lab docker clean <project>`; `rm` and `rmi` stay free. A command that creates (those, `pull`, `compose up`) checks the room cached in `$LAB_STATE/docker-room` (read at most once a minute in 2 s, written by `lab docker clean`; Docker missing or silent → passes): short → `lab docker clean <project> && <command>`, still short within 10 min of that project's clean → refused, the rest is not the project's. Each refusal gives the exact line (`Run instead:`), built on the raw command, which passes the guard; a quoted literal is read, an expansion (`$VAR`, `$(…)`) is not; `LAB_FORCE=1` lifts it; `docker` inside a script or `bash -c "…"`, a `docker` word broken on purpose (`d''ocker`, an expansion: the pre-filter reads the raw text), or a command too long to read within the hook's time, is not read — the guard helps a cooperating agent, it is not a wall.

## Evidence outside the repository: lab proof

A batch's evidence files (screenshots, outputs, measurements) go neither into the repository nor into a hand-written manifest script: `lab proof` stores them under `state/preuves/<project>/<lane>/lot-NN-<slug>/` of the installation, one `manifest.json` per batch.

- `lab proof [project] <batch> add [--step <name>] <files…>`: `<batch>` is `lot-NN-<slug>` or `<slug>`, looked up in the batch files of the main checkout and of each lane (refusal naming the lanes read, or the two lanes of a shared slug). `--step` (`^[a-z0-9][a-z0-9._-]*$`, `general` by default, `manifest.json` reserved) stores the copies under `<step>/<name>`. Each argument must be a readable regular file; the whole list is validated before the first write. A copy is checked by its own fingerprint before being placed; a mismatch removes the call's copies and leaves the manifest intact.
- Versioned file: tracked in the project repository (main checkout or lane) or in the batch files repository, and identical to HEAD → no copy, `source=git` entry with `repo` (`projet` or `fiches`), `path`, `commit` and `blob`: the blob survives a squash merge as soon as the same content is on the base branch. Modified, untracked, ignored or outside a repository → copy (`source=copie`, `path`, `bytes`).
- `manifest.json` v1: `{"version":1,"project","lane","lot","files":[…]}`, each entry with `step`, `name`, `sha256`, `added` (`lab now`). Same step, same name, same fingerprint → skipped (`PROOF_SKIPPED`); other fingerprint → refusal quoting both fingerprints and suggesting `--step`.
- Output: `PROOF_BATCH`, `PROOF_LANE`, `PROOF_ADDED` (copies), `PROOF_GIT` (references), `PROOF_SKIPPED`, `PROOF_MANIFEST_SHA256`; one line per file on stderr.
- `lab proof [project] <batch> verify`: one block per entry (`PROOF_FILE`, `PROOF_SOURCE`, `PROOF_STATUS=ok|altered|absent`), then `PROOF_OK`, `PROOF_BAD`, `PROOF_EXTRA` (files placed by hand outside the manifest, named, warning only); rc 1 if a piece of evidence is altered or missing, if the manifest is missing or unreadable. A batch whose batch file left with its lane (`docs=repo`) is found through its evidence folder. `--json` on both forms.

The evidence report (`lots/<lane>/preuves/lot-NN-<slug>.md`) quotes the command and `PROOF_MANIFEST_SHA256`, never an absolute path. `lab close` never removes this evidence.

## Batch file size and broken hooks

`lab doctor` measures `<project>.batch_files.size`, without ratchet: the bytes of the heaviest `lot-NN-<slug>.md` batch file in `lots/` and `lots/<lane>/` (`preuves/`, briefs and CHANGELOG excluded; 1 KB = 1,000 bytes). Above 30,000 bytes: warning; above 60 000: red for a batch file whose `**Créé**` line is dated 2026-09-16 or later, warning only for an older or undated batch file. The note names the three heaviest and the remedy: move the log narrative to `lots/<lane>/preuves/lot-NN-<slug>.md` while keeping the link. `<project>.hooks.broken` names each command not found: `<file> : <event> → <command>`, five at most. The `--report` mode keeps status and value, never a batch file name or a command. `<project>.ci.workflows` warns, never red, for each workflow in `.github/workflows/` triggered on `pull_request` without a draft guard, without `concurrency` or on `push` of any branch: `<file> : <missing guards>`, remedy `modèle templates/project/ci.yml`; lab never overwrites a workflow: `lab new` commits that template (`chore(ci)`, `CI_TEMPLATE=written`) only in a lane of a project without any workflow, `kept` otherwise. `<project>.ci.minutes_week` (≤ 1,500 equivalent minutes, macOS × 10), `ci.runs_per_pr` (≤ 3), `ci.heavy_pr_jobs` (0 pull request job over 15 min outside `full-suite`) and `ci.night_red_days` (≤ 2) cover the last 7 days, read from `state/ci-<project>` that `lab next` and `lab close` refresh in the background at most once a day (gh); warning above the limit, red above both the limit and the baseline; no cache or older than 7 days: `ci.measures` `not measured`. A project red stops `lab merge` and `lab close`; when `ci.night_red_days` is the only one and the lane proves its fix (green manual night, see `lab close`), delivery continues with a named warning (`DOCTOR_NIGHT_PROOF=<run>`).

## Timestamps and deadlines

`lab now` prints only the UTC instant `AAAA-MM-JJTHH:MM:SSZ` on stdout, identical on macOS and Linux (clock read in POSIX format, arithmetic in awk, never GNU nanoseconds); `lab --json now` returns `NOW`. `LAB_NOW=<AAAA-MM-JJTHH:MM:SSZ>` sets the clock of `lab now`, `lab due` and session startup (tests, reproduction); a malformed value is refused by quoting it.

A project's deadlines live in `projects/<project>/echeances`, one file for all its lanes, written by `lab due` alone — never by hand, never in a batch file. Format `treelab v1`: header `# échéances de <project> — treelab v1 : …` (which carries the last id given), then one line per deadline, five tab-separated fields `id⇥échéance⇥état⇥objet⇥décision`. A `AAAA-MM-JJ` deadline is due until the end of that UTC day, `AAAA-MM-JJTHH:MM:SSZ` until that instant; the state is `ouverte`, `faite` or `annulée`; an id is never given again; an unreadable line is named by its number and kept.

- `lab due <project>`: overdue (oldest first), within 48 h, upcoming; `DUE_LATE`, `DUE_48H`, `DUE_OPEN`, then one block per deadline (`DUE_ID`, `DUE_DATE`, `DUE_STATUS`, `DUE_SUBJECT`); under each overdue one, the three decisions ready to type.
- `lab due <project> add <deadline> <subject…>` → `DUE_ID`; a past date is accepted with the warning `déjà en retard`.
- `lab due <project> done <id> <sha>`: the commit must exist in the project repository or in the batch files repository; otherwise `cancel`.
- `lab due <project> reschedule <id> <deadline>`: the new deadline must be in the future (`lab now`).
- `lab due <project> cancel <id> <reason…>`: reason required.

After each write, `lab due` records that single file in its git repository: `DUE_COMMIT=<sha>`, `DUE_COMMIT=none` (`DUE_REASON`: no repository, treelab code checkout in dev mode, repository of a registered project) or `DUE_COMMIT=failed` (git message); the write stays done.

At the start of a project session, the context carries at most one line: `DUE: <n> overdue, <m> within 48 h — lab due <project>` (nothing if there is neither overdue nor 48 h). An overdue deadline already seen by another session and still open comes first: `DUE=RED <n> overdue deadline(s) left unsettled since an earlier session (no. …)` — relay it to the user first, then settle it with `lab due`. A resumption of the same session does not count; the doctor's measurement mode shows nothing.

Update rights, from a local cache written by a successful `treelab update` (never the network): `lab status` gives `LICENSE_PLAN`, `LICENSE_UNTIL`, `LICENSE_STATE=active|ending|ended|none` and `LICENSE_CHECKED` (nothing before a first reading), the doctor `install.entitlement` (warning, never red). A trial or a cancelled subscription less than 2 days from its end, or ended rights, bring one line a day at the first `lab next` and, once a day, `LICENSE=ENDING|ENDED …` at the head of the session context: relay it to the user first, in their language. `lab subscribe` keeps the key: a trial key becomes paid, a cancelled or unpaid subscription opens its Stripe page; with a terminal it waits for the payment (30 minutes at most, q then Enter stops), without one (an agent) it opens the page and returns `RESULT=opened` — let the user pay, never fill in the payment.

## Installation: local release and import of an earlier installation

- Publishing: `scripts/publier.sh <version> [--trial]`, from a checkout of the repository, refuses with the cause if `VERSION` or the `## <version>` section of the `CHANGELOG.md` of `origin/main` do not match, if the CI of `origin/main` is not green or if the tag `v<version>` is on another commit; then proves the real upgrade from the previous published version (highest remote `vX.Y.Z` tag below) through `scripts/prouver-montee.sh <from> <to>` (throwaway HOME, `release-local.sh --install`, `lab setup`, `treelab update` of the code being left): `UPGRADE=ok FROM=<previous>`, otherwise `UPGRADE=red`, `PUBLISHED=red` and no tag, `--trial` included; a copy differing from `origin/main` reruns itself from its tree extracted into a throwaway folder (trace on stderr); otherwise places and pushes the annotated tag, waits for the tag's `release.yml` run and returns `PUBLISHED=ok|red|already` with `RUN=<link>`, then `CATALOG=ok|red` through `lab update --catalogue` (licence `~/.lab/license`) or `CATALOG=not-verified` without a licence. `--trial`: all the checks, nothing placed or pushed (`PUBLISHED=trial`). Pushed tag = public action: run by the user, or by an agent on their explicit request only.
- Local release: `scripts/release-local.sh <revision> <folder>` builds from the committed tree `treelab-<VERSION>.tgz` (program only, `.release` added, validated as `lab update` reads it) and `latest.json` (`version`, `url` as `file://`, `sha256`); an archive of the same version with different content is refused: bump `VERSION`. `--install` creates `~/.lab/releases/treelab-<VERSION>` and `~/.lab/current` if they do not exist; otherwise `LAB_UPDATE_SOURCE=file://<folder>/latest.json treelab update`, rollback via `treelab update --rollback`.
- Update: `lab next` installs on its own, at most once a day, the latest minor or patch (live sessions included, they keep their release; the next session starts from the new one and announces it, rollback via `treelab update --rollback`); a major, `auto_update=no` in `~/.lab/config` or a missing licence only bring a line naming the remedy; never blocking. `treelab update` is refused only during a lab operation. Adopting an earlier install (0.1.1, whose client refuses live sessions): the installer extracts the archive into `~/.lab/releases/treelab-<NEW>` then runs `LAB_UPDATE_SOURCE=file://…/catalogue.json ~/.lab/releases/treelab-<NEW>/bin/lab update --adopt`; sessions kept, each takes the new version at its restart; output `RESULT=adopted|current|refused|interrupted` (`refused`: `REASON=operation|layout|version|archive|source`, nothing modified; `interrupted`: resume via `treelab update --resume`); rollback via `treelab update --rollback` → `RESULT=restored`. Outside `--adopt`, any failure of `treelab update` (update, `--rollback`, `--resume`, `--catalogue`; not usage, rc 2) ends with a single `RESULT=refused` (nothing modified) or `interrupted` (`update-pending` left: `--resume`), `REASON=operation|layout|version|archive|source|network|licence|entitlement` and `FILE=<chemin>` when a file is involved (`entitlement`: update rights ended, the line gives the end date and names `lab subscribe`, the installed version keeps working); the plan of `setup` and `update` sums up the objects already in place in one line `Keep: N items already in place (details: <file>)`, detail outside the account next to the operation lock.
- `~/.lab/current/bin/lab setup --import <copy>`: a single reversible install. Links leading into the copy (`lab` command, instructions, skill and agent folders) are replaced, the `<copy>/hooks/…` hooks removed in the same merge (third-party hooks kept; the copy is recognized on disk, case included), ordinary Codex agents bearing a treelab agent's name replaced with a backup, the copy's skills absent from treelab kept discoverable through a link; `lab uninstall` restores each link, hook and file.
- Data copied into `LAB_HOME` before the transaction, never moved: each branch of the copy at its revision (notes and every stash entry included) and a head commit that tracks only `projects/`, `config`, `.gitignore`; `projects/` as is (without the copy's own entry); `agent=` from `preferences` into `config`; `state/` without `backups/`; space checked before copying; a rerun answers "already imported". The copy is never written.
- Each reference to the copy that the install does not own comes out as `LEFT=<category> <file> — <marker>` (`plugins`, `trust`, `hook` — any hook quoting the copy outside `<copy>/hooks/` —, `scheduled`, `skill`, `project`, `other`), never modified: to settle with the user before renaming the copy. `--dry-run` prints the plan, the `IMPORT_*` figures and the inventory, then names the live sessions that will block the install (rc 1); the real install refuses before any write as long as a session lives in a treelab or copy project.

## Default agent: a single rule

`option > lane > project > global > default`: `--agent` on the command, then `agent=` in the lane's `.lab/meta` (set by `lab new`, `lab open --agent`, `lab launch`, `lab next`), then `agent=` in `projects/<project>/config` (empty without `lab init --agent`), then `agent=` in `LAB_HOME/config` (`KEY=value` file edited by hand, no command writes it), finally `claude`. `lab status` shows the retained value and its source: `AGENT=claude (default)`, `AGENT=codex (global <file>)`, `AGENT=claude (project <file>)`, per lane `AGENT=codex (lane <file>)`. A value outside `claude|codex` is shown with a note by `lab status`, and refused by `lab new`, `lab open`, `lab launch` and `lab next` by naming the file and the value read.

Session named by default: every Claude session opened by lab (`launch`, `next`, `new`, `open`, replacement, onboarding) receives `--name <lane>`, or `--name <project>-main` in the main checkout — name visible in the input area and in /resume; the cmux tab's explicit title is not touched. Codex has no name option at launch: its session is not named.

## Safety rules

A project keeps a main checkout without commits and worktrees under .worktrees/. One branch per batch, one active batch per lane, one live session per lane. Never use git worktree directly.

A session lock is removed only by a command that opens a session (`lab next`, `lab launch`, `lab open`) or by the end of the session itself, and only if its process is proven dead (`kill -0` failing **and** `ps` empty). A read (`status`, `plan`, `sweep`, `doctor`) never deletes anything; under a sandbox, a refused signal does not count as death: the `uncertain` state keeps the lock and the command says so.

The Bash guard protects destructive operations. When an explicit request that is safe hits a false mechanical block, the agent applies the authorized workaround itself; it never hands this mechanism back to the user. Delivery checks, however, remain mandatory.

`LAB_FORCE=1` applies to the single segment it prefixes (`LAB_FORCE=1 git reset --hard`; `LAB_FORCE=1 true; git reset --hard` stays refused) or to the whole session if it is in the environment. It never lifts a silent loss: force push (`--force`, `--mirror`, refspec `+…`) or deletion towards `main`, `staging`…, `merge|rebase|cherry-pick|pull -X ours|theirs` and `-s ours`, `checkout|restore --ours|--theirs`. Forceable refusals: `checkout <réf> -- f` and `restore --source <réf>` from a branch other than `HEAD` or the base (`git diff <réf> -- f`, then the wanted lines); `stash pop`, `drop`, `clear`, `apply` without SHA (the stack is shared by all sessions: WIP commit, or `stash push -m <étiquette>` then `stash apply <sha>`).

In the batch files repository and the main checkout, the index serves every session: a `git commit` names its paths (`git commit -m <message> -- <files>`); without paths, with `-a`, `--amend` without paths or `.` and `:/` as path, it is refused (forceable). In the main checkout, `git add -A`, `-u`, `.` and `:/` are refused, `git add <files>` passes. Lanes stay free.

In development, `LAB_INSTALL_ROOT` explicitly designates the stable installation that `lab doctor` must check if the tested CLI comes from another checkout. Link, hook and baseline checks all stay active.

The acceptance lives only in the `## Recette du couloir` section of the last batch file: agreement, date (`AAAA-MM-JJ`, free suffix accepted after the date), tried revision (complete, backticks accepted) and evidence. It must be versioned, including with external documents whose `**Révision des documents**` is also recorded before the trial; a change outside that section requires a new trial. It is written and recorded by `lab acceptance`, never by hand; `lab close <project> <lane> --dry-run` then lists all remaining obstacles. After an explicit closing agreement already received, an agent uses `lab close <project> <lane> --confirm <lane>`. `LAB_FORCE` waives no closing check. An old branch whose attribution is no longer proven stays present, even if its name appears in a batch file.
